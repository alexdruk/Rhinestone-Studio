# RS-0003.5C2 — Unified Rendering Pipeline

## Objective

Complete the separation between geometry generation and rendering. Extract the 2D production
canvas renderer, the cup preview renderer, and the SVG exporter out of `app.js` and into permanent
`src/renderer/**` / `src/export/**` modules that consume only `StoneLayout` (from
`src/geometry/StoneLayout.js` / `Stone.js`) — never `project.layers`, never a layer `type`. `app.js`
keeps ownership of everything that legitimately requires layer/selection awareness (editor
selection outline/handles, grid, HUD text, drag/resize UI), and becomes the orchestrator that
generates one `StoneLayout` per update and hands the same object to every renderer and exporter.

## Current Repository State

* RS-0003.5C1 finished routing text, circle, and rectangle layers through the permanent
  `src/geometry/GeometryEngine.js`, so every layer's stones already arrive as `Stone` instances
  (`xMm`, `yMm`, `sizeMm`, `color`, `layerId`) inside a per-layer `StoneLayout`.
* `app.js`'s local (legacy, in-file) `GeometryEngine.generate(project)` still converts those
  per-layer `Stone` instances back down into ad hoc plain objects (`{x,y,d,color,layerId}`),
  concatenates them across layers, runs a proximity `dedupe()`, and returns a hand-built plain
  object `{version,units,canvas,stones,bbox,stats}` — not a real `StoneLayout`.
* `app.js` also still owns all rendering: `drawStone2D()` (shared stone-drawing primitive),
  `drawLayout()` (2D production canvas: background, grid, stones, selection, HUD text),
  `drawCup()` (cup body + wrapped stone projection), and `svg()` (SVG export), plus the
  `STONE_COLORS` display palette they all read from.
* `src/renderer/README.md` and `src/export/README.md` already state the intended contract
  ("renderers/exporters must consume Geometry Engine output instead of generating stones
  themselves") but `src/renderer/**` and `src/export/**` contain no code yet — every prior
  milestone's guard tests explicitly forbade touching them until this milestone.
* PNG and Cup PNG "export" already happen via `canvas.toBlob()` on the same `layoutCanvas` /
  `cupCanvas` that were just drawn from the same `layout` object, so they already trivially satisfy
  "consume the same generated layout" once the renderer that draws those canvases does.
* Project JSON export (`JSON.stringify(project)`) and Generated Layout JSON export
  (`JSON.stringify(layout)`) already read from the single `project` / `layout` state app.js holds.

## Expected Visible Change

* None. Stone positions, sizes, colors, cup projection math, and SVG output are pixel-for-pixel
  and coordinate-for-coordinate identical — this milestone moves code, it does not change any
  formula, constant, or sampling algorithm.
* One deliberate, self-consistent schema change: "Export Generated Layout JSON" now serializes the
  real `StoneLayout.toJSON()` (`{layerId, sourceMode, count, boundingBox, widthMm, heightMm,
  stones:[{xMm,yMm,sizeMm,color,layerId,index,metadata}]}`) instead of the old ad hoc
  `{version,units,canvas,stones:[{x,y,d,color,layerId}],bbox,stats}` shape. This is the direct,
  required consequence of "Layout JSON... consume[s] the same generated layout" — the export is now
  literally the canonical `StoneLayout`, not a lookalike. All manufacturing-relevant data (stone
  positions in mm, size, color, layer id, total count, bounding box) is preserved, only reshaped
  to the canonical field names.

## Required Outcome

* `src/renderer/CanvasRenderer2D.js` (new): exports `drawStone()` (single-stone canvas primitive),
  `fitTransform()` (pure mm-bbox → px-viewport transform math), `drawGrid()`, `renderStoneLayout()`
  (draws every stone in a `StoneLayout`), and `renderProductionLayout()` (background + grid +
  stones for the 2D canvas, given a `StoneLayout` and a viewport). None of these take a `Layer`,
  a `Project`, or a layer `type`.
* `src/renderer/CupRenderer.js` (new): exports `renderCup()` — the full cup body, handle, and
  wrapped/front stone projection, given a `StoneLayout` and display options (`cupColor`, `wrap`,
  `rotationDeg`, `zoom`). No layer/type awareness.
* `src/renderer/StoneColors.js` (new): the `STONE_COLORS` display palette, moved verbatim out of
  `app.js` so both renderers and the SVG exporter share one definition instead of three copies.
* `src/export/SvgExporter.js` (new): exports `stoneLayoutToSvg()`, given a `StoneLayout` and
  `{widthMm,heightMm}`. No layer/type awareness.
* `app.js`'s `generate(project)` returns a real `StoneLayout` (`layerId: 'project'`, i.e. the
  merged, cross-layer product; every contained `Stone` keeps its own real `layerId`) built by
  merging the per-layer `StoneLayout`s the permanent engine already returns and running the
  existing proximity `dedupe()` over their `Stone` instances (field names only: `.x/.y/.d` →
  `.xMm/.yMm/.sizeMm`; no change to the dedupe algorithm itself).
* `app.js`'s `drawLayout()` calls `renderProductionLayout()` for background/grid/stones, then
  keeps drawing the (layer-aware) selection outline/handles and HUD text itself, using the
  transform `renderProductionLayout()` returns.
* `app.js`'s `drawCup()` becomes a thin call to `renderCup()`.
* `app.js`'s SVG export button calls `stoneLayoutToSvg()`.
* Geometry generation happens exactly once per `updateAll()` call (inside `generate()`); every
  renderer and exporter is handed that same `StoneLayout` instance — no renderer or exporter
  recomputes or mutates stone positions.
* Neither renderer, nor the SVG exporter, contains a reference to `layer.type`, `'text'`,
  `'circle'`, or `'rectangle'`.
* Stone size, gap, color, layer ID, bounding box, and deterministic output are preserved.
* Shape/text editing (add, select, drag, resize, duplicate, delete, visibility) remains functional,
  unchanged, since none of it depended on how rendering was organized internally.

## Architecture Requirements

* `src/renderer/**` and `src/export/**` have zero dependency on `project.layers`, `Layer`, or any
  layer `type` string — enforced by a new automated test.
* `src/renderer/**` may depend on the DOM Canvas 2D API (`CanvasRenderingContext2D`); that is its
  job. `src/export/**` (SVG) must not touch the DOM/Canvas at all — pure string generation from a
  `StoneLayout`.
* `src/geometry/**` is untouched by this milestone (no changes needed; it already produces
  `Stone`/`StoneLayout`).
* The merged multi-layer `StoneLayout` returned by `app.js`'s `generate()` uses the sentinel
  `layerId: 'project'` because `StoneLayout`'s constructor requires a single non-empty
  `layerId` string and was designed as a per-generation-call product; every `Stone` inside it
  still carries its own real layer id, which is what layer-aware code (selection bounding box,
  visibility) filters on. Changing `StoneLayout`'s constructor contract to natively support a
  multi-layer aggregate is out of scope for this milestone (see Out of Scope).

## Out of Scope

* Redesigning the UI, improving cup appearance, changing cup rotation behavior.
* Removing the legacy in-`app.js` bitmap text engine or legacy `generateCircle`/`generateRect`
  (still unused, still preserved, per existing precedent).
* Optimizing performance, adding new shapes, changing the project JSON schema.
* Moving the cross-layer `dedupe()` merge step into the permanent `src/geometry/GeometryEngine.js`.
  It only filters already-generated `Stone`s by proximity (it invents no new positions), so leaving
  it in `app.js`'s orchestration step does not violate "geometry generation occurs exactly once."
  Consolidating it into the permanent engine is reasonable future work, not required here.
* Changing `StoneLayout`'s constructor to natively support multi-layer aggregates (see Architecture
  Requirements) — the `layerId: 'project'` sentinel is sufficient for this milestone's outcome.
* Fixing the previously recorded, pre-existing visual issues (cup handle appearance, cup drag
  rotation sensitivity, stone-size dropdown blank-selection bug) — record only, do not fix.
