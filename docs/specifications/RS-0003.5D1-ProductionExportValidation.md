# RS-0003.5D1 — Production Export Validation & Compatibility

## Objective

Make every export trustworthy, internally consistent, and traceable to the same canonical
`StoneLayout` that RS-0003.5C2 already made the single source of truth for the 2D canvas, cup
preview, and exporters. This milestone does not change how geometry is generated or rendered — it
closes the remaining gaps between "the exports read from the right object" (already true since
RS-0003.5C2) and "the exports are validated, documented, and round-trip losslessly" (not yet
true): there is currently no Project JSON *import* path, `SvgExporter.js` accepts any input
without validation, export button handlers can throw an unguarded error if clicked before the
first successful generation, and the Generated Layout JSON schema is described only informally in
`docs/ARCHITECTURE.md` prose, not as a documented schema with a compatibility finding.

## Current Repository State

* RS-0003.5C2 already made `app.js`'s `generate(project)` return a real `StoneLayout`
  (`layerId:'project'` sentinel; every contained `Stone` keeps its own real layer id), and wired
  the 2D canvas (`renderProductionLayout`), cup preview (`renderCup`), and SVG export
  (`stoneLayoutToSvg`) to consume that same object. PNG/Cup PNG export is `canvas.toBlob()` against
  whichever canvas the renderer most recently drew, in the same `updateAll()` pass. Generated
  Layout JSON export is `JSON.stringify(layout, null, 2)`, and because `layout` is a real
  `StoneLayout` instance, `JSON.stringify` already calls its `toJSON()` — the export is already the
  canonical schema, not a lookalike.
* A repository-wide search (`grep -rn` across `tools/**`, `examples/**`, `app.js`) found **no**
  remaining reference to the pre-RS-0003.5C2 ad hoc Generated Layout JSON shape
  (`{version,units,canvas,stones:[{x,y,d}],bbox,stats}`). The only `x:`/`y:`/`d:` object-literal
  hits in `tools/**` are `test-render-export-pipeline.mjs`'s fake-canvas `arc(x,y,r)` call
  recorder, unrelated to the old stone-layout schema. **Finding: no versioned compatibility layer
  is needed** — the schema migration that RS-0003.5C2 made is already complete repository-wide.
  This milestone documents that finding instead of building unneeded compatibility machinery.
* `app.js` has an "Export Project JSON" button (`JSON.stringify(project, null, 2)`) but **no
  import path at all** — no file input, no "Import Project JSON" button, no parse/validate/load
  function. `project` is `app.js`'s ad hoc plain-object model (`defaultProject()`), not
  `src/core/Project.js` — a deliberate, test-enforced exclusion carried forward from RS-0003.5B3
  (see `docs/ARCHITECTURE.md`, "Current Architectural Limitations" #1). This milestone does not
  change that; it adds import/round-trip capability for the ad hoc schema the live app already
  exports, since migrating `app.js` onto `src/core/Project` remains explicitly out of scope (see
  "Out of Scope" below and the milestone brief).
* `stoneLayoutToSvg()` (`src/export/SvgExporter.js`) has no input validation: a missing/malformed
  `stoneLayout` or a non-numeric/non-positive `widthMm`/`heightMm` produces either a thrown
  low-level error deep in a `for` loop or a malformed SVG string, not a clear, typed failure.
* `app.js`'s five export button handlers (`#exportProject`/`#exportLayout`/`#exportSVG`/
  `#exportPNG`/`#exportCup`) call `download()`/`exportCanvas()` unconditionally. `#exportLayout`,
  `#exportSVG`, `#exportPNG`, and `#exportCup` all read `layout`, which is `null` until the first
  `updateAll()` call resolves (it is `async`); clicking one of those buttons in that window throws
  an unguarded `TypeError` instead of a clear message, and no `try`/`catch` surrounds any export
  handler, so a thrown error from (for example) the new `SvgExporter` validation would also be
  unguarded.
* `stoneLayoutToSvg()`'s `<circle>` elements carry only the *display* color (fill/stroke hex looked
  up from `STONE_COLORS`), not the stone's original color id (`s.color`, e.g. `'gold'`) — the
  manufacturing-relevant color metadata that Generated Layout JSON already preserves per-stone is
  silently dropped from the SVG.
* `Stone.js`/`StoneLayout.js` already have `toJSON()`/`fromJSON()`, exercised by
  `tools/test-geometry-engine.mjs`'s determinism assertions (`assert.deepEqual(first.toJSON(),
  second.toJSON())`) but there is no dedicated schema/round-trip test file for `Stone`/
  `StoneLayout` themselves (as opposed to `GeometryEngine`'s generation output).
* `src/core/Project.js` already has a full serialize/round-trip test
  (`tools/test-core-model.mjs`, `Project.fromJSONString(original.toJSONString())`), but that model
  is not what the live app exports/imports (see above) — it is out of scope to change or retarget
  this milestone's Project JSON work onto it.

## Expected Visible Change

* New "Import Project JSON" button + hidden file input in the left control panel (`index.html`),
  directly above the existing "Export" section. Selecting a valid, previously-exported project
  file loads it (replacing the current in-memory project, regenerating the layout, canvas, and cup
  preview) and reports success in the status line. Selecting an invalid file leaves the current
  project untouched and reports a specific error in the status line (e.g. which layer/field failed
  validation) instead of throwing or silently corrupting state.
* Exported SVG `<circle>` elements gain a `data-color="<id>"` attribute carrying the stone's
  original color id (e.g. `data-color="gold"`), in addition to the existing display `fill`/
  `stroke`. No existing SVG attribute changes value or is removed.
* Clicking an export button before the first layout has generated (or if an exporter rejects its
  input) now shows a specific error in the status line instead of an uncaught exception in the
  console.
* No change to 2D layout, cup preview, stone positions/sizes/colors, or the Project JSON / Layout
  JSON schemas themselves.

## Required Outcome

* **Project JSON round-trip.** `app.js` gains an import path (button + hidden file input) that
  reads a `.json` file, validates it against the same ad hoc shape `defaultProject()`/
  `JSON.stringify(project)` already produce (top-level `canvas.width`/`canvas.height` positive
  numbers, non-empty `layers` array, each layer has a unique string `id`, a `type` in
  `{text,circle,rectangle}`, and that type's required numeric/string fields, plus a positive
  `stoneSize` and non-negative `gap`), and on success replaces `project`, regenerates the layout,
  and re-renders every consumer. On failure, `project` is left untouched and a specific error is
  shown. Round-tripping an file this app itself exported must always succeed and must not silently
  drop any layer or field.
* **Generated Layout JSON is documented.** `src/geometry/README.md` gains a "Generated Layout JSON
  Schema" section describing every field `StoneLayout.toJSON()`/`Stone.toJSON()` produce, with a
  worked example, so the schema is discoverable without reading source.
* **SVG dimensions stay explicit millimeters** (already true — `width="<n>mm" height="<n>mm"
  viewBox="0 0 <n> <n>"`); add a regression test.
* **SVG stone count, coordinates, sizes, and bounds match the canonical `StoneLayout`** (already
  true by construction — `stoneLayoutToSvg()` iterates `stoneLayout.stones` directly); add
  regression tests covering count, every stone's `cx`/`cy`/`r` (not just the first), and the SVG's
  implied bounds (min/max over every circle's footprint) against `stoneLayout.getBoundingBox()`.
* **2D PNG / Cup PNG are produced from the same rendered `StoneLayout`** (already true — PNG export
  is `canvas.toBlob()` against the canvas the renderer just drew from `layout` in the same
  `updateAll()` pass); add a structural regression test guarding this call order does not regress,
  and a browser-verified stone-count cross-check.
* **No exporter or renderer regenerates geometry** (already true structurally — none of
  `CanvasRenderer2D.js`/`CupRenderer.js`/`SvgExporter.js` import `GeometryEngine` or call
  `generateTextLayout`/`generateShapeLayout`); add an explicit regression test (previously only
  implied by the "no layer/type reference" test).
* **Color metadata preserved where the target format supports it.** Generated Layout JSON already
  preserves `Stone.color` verbatim. SVG gains a `data-color` attribute per circle (SVG supports
  custom `data-*` attributes; this is additive, not a schema-breaking change to existing consumers
  of `fill`/`stroke`). PNG is a raster format with no practical, dependency-free way to embed
  per-stone color metadata — out of scope, consistent with "do not add new export formats."
* **Deterministic exports are tested where practical.** Add: two calls to `stoneLayoutToSvg()` with
  an identical `StoneLayout` produce byte-identical output; `StoneLayout.toJSON()` round trips
  through `fromJSON()` losslessly and deterministically.
* **Export failures surface clearly instead of silently producing invalid files.**
  `stoneLayoutToSvg()` throws a clear, typed error (`TypeError`) for a missing/malformed
  `stoneLayout` or a non-positive/non-finite `widthMm`/`heightMm`, instead of throwing deep inside
  a loop or emitting a malformed string. Every `app.js` export button handler checks its
  preconditions (`layout` present) and wraps the export call in `try`/`catch`, reporting a specific
  message via `#status` on failure rather than throwing.

## Required Compatibility Work

* Document the current Generated Layout JSON schema — see "Required Outcome" above
  (`src/geometry/README.md`).
* Identify whether any example, test, or repository code depends on the old `x`/`y`/`d` layout
  schema — **done, during specification drafting** (see "Current Repository State" above):
  repository-wide search found none. No versioned compatibility strategy is implemented, because
  none is needed; this finding itself is the required compatibility deliverable for this
  milestone.
* The Project JSON schema is not changed. The import path validates against the exact ad hoc shape
  `app.js` already exports; it does not introduce a new schema or a second Project representation.

## Architecture Requirements

* `src/export/SvgExporter.js` remains pure string generation with no DOM/Canvas dependency and no
  knowledge of `Project`/`Layer`/layer `type` — validation added this milestone only inspects the
  shape of its own two parameters (`stoneLayout.stones`, `widthMm`, `heightMm`), not project/layer
  concepts.
* The new Project JSON import path lives entirely in `app.js` (orchestration layer, per
  `docs/ARCHITECTURE.md`'s "Orchestration Layer" section) and validates against `app.js`'s own ad
  hoc project shape — it must not import or construct `src/core/Project`/`Layer` (migrating onto
  that model remains a separate, larger, explicitly out-of-scope milestone).
  `app.js`'s existing import allowlist (`src/geometry`, `src/fonts`, `src/text`, `src/renderer`,
  `src/export`, `src/browser/BrowserDependencyProbe.js`) does not change. The import handler reads
  a `File` via the browser's `File`/`FileReader` API only — no new dependency — and is intentionally
  symmetric with the existing `#exportProject` handler.
* No renderer or exporter gains a dependency on `src/geometry/GeometryEngine.js` or calls
  `generateTextLayout()`/`generateShapeLayout()` — this was already true and is now covered by a
  regression test.
* `src/geometry/**` is untouched (documentation-only addition to `src/geometry/README.md`).

## Out of Scope

* Redesigning the UI, improving cup visuals, tuning cup rotation.
* Removing legacy/dead code (`app.js`'s bitmap text engine, legacy shape generators,
  `engine.bbox()`/`layerBBox()`) — still recorded as a future cleanup candidate.
* Migrating `app.js`'s ad hoc project/layer objects onto `src/core/Project.js`/`Layer.js`. The
  import path validates and loads the *existing* ad hoc schema; it does not change which project
  model `app.js` uses.
* Repairing font-manifest data (`enabled` flags, the `roboto-mono-regular` placeholder stub).
* Adding new export formats (DXF, manufacturing reports) or new geometry/shape types.
* Optimizing performance.
* Consolidating the cross-layer `dedupe()` merge step into `src/geometry/GeometryEngine.js`, or
  changing `StoneLayout`'s single-`layerId` constructor contract — unrelated to export validation.
* Embedding color metadata in PNG exports (no practical dependency-free mechanism; raster formats
  are explicitly not required to carry it per "Required Outcome").
* Import validation that reconstructs or repairs a malformed project — invalid input fails clearly
  and is rejected, not "fixed up" silently.

## Required Automated Tests

Add `tools/test-production-export-validation.mjs` verifying:

1. `Stone`/`StoneLayout` schema and round-trip: construct a multi-stone `StoneLayout`, call
   `toJSON()`, assert every documented field is present with the correct type/shape, call
   `StoneLayout.fromJSON()` on the result, and assert the reconstructed instance's `toJSON()` is
   deep-equal to the original (lossless round trip).
2. `StoneLayout.toJSON()` determinism: building the same `StoneLayout` twice from identical inputs
   produces deep-equal `toJSON()` output.
3. SVG width/height/viewBox are explicit millimeters and numerically consistent with each other and
   with the input `widthMm`/`heightMm`.
4. SVG `<circle>` count equals `stoneLayout.count` for a multi-stone, multi-layer-id layout.
5. Every SVG `<circle>`'s `cx`/`cy`/`r` matches its corresponding stone's `xMm`/`yMm`/`sizeMm/2` (to
   3 decimals) — not just the first stone.
6. The SVG's implied bounds (min/max of every circle's `cx±r`/`cy±r`) equal
   `stoneLayout.getBoundingBox()` (within rounding tolerance).
7. Every SVG `<circle>` carries `data-color="<stone.color>"` matching the source `Stone.color`.
8. `stoneLayoutToSvg()` is deterministic: two calls with the same `StoneLayout` produce
   byte-identical strings.
9. `stoneLayoutToSvg()` throws a clear `TypeError` for: a missing/`null` `stoneLayout`; a
   `stoneLayout` without a `stones` array; a non-numeric, non-finite, zero, or negative `widthMm`;
   same for `heightMm`.
10. `CanvasRenderer2D.js`, `CupRenderer.js`, and `SvgExporter.js` source text contains no reference
    to `GeometryEngine`, `generateTextLayout`, or `generateShapeLayout` (no exporter/renderer
    regenerates geometry).
11. Passing two different `StoneLayout`s to `stoneLayoutToSvg()` produces two different strings
    (output is driven by the provided layout, not hardcoded).
12. A representative fixture matching `app.js`'s ad hoc project shape round-trips losslessly through
    `JSON.parse(JSON.stringify(fixture))` (`deepEqual`) — confirms the exported/imported shape is
    plain-JSON-safe end to end.
13. Structural checks on `app.js`: it defines a project-import handler wired to a file input
    (`#importProjectFile`) and an `#importProject` button; the handler validates required fields
    before assigning to `project` (e.g. checks `Array.isArray` on `layers`); parse/validation
    failures are caught and reported via `#status`, not thrown; `#exportLayout`/`#exportSVG`/
    `#exportPNG`/`#exportCup` each guard on `layout` being present before exporting; all five export
    handlers are wrapped in `try`/`catch`.
14. Structural check on `index.html`: contains an `#importProject` button and an `#importProjectFile`
    file input.
15. No forbidden file changed (this milestone's own forbidden list).

Update the two existing guard tests that currently forbid `index.html` in their "no forbidden file
changed" assertion (`tools/test-render-export-pipeline.mjs`, `tools/test-shape-geometry-integration.mjs`)
to remove it from their forbidden-exact set, since this milestone legitimately changes it —
following the same narrow-update precedent RS-0003.5C2 applied to seven prior guard files for
`src/renderer/`/`src/export/`.

Run the full suite (`npm test`) and confirm all prior suites still pass.

## Acceptance Criteria

* `npm test` passes, including the new suite.
* Project JSON round-trips losslessly for any project the app itself exports; invalid imports are
  rejected with a specific, visible error and do not corrupt in-memory state.
* SVG/Layout JSON/PNG/Cup PNG exports are verified — via automated test and browser inspection — to
  match the canonical `StoneLayout` in count, coordinates, sizes, and bounds.
* Export failures (bad input, `layout` not ready) surface a specific message instead of an
  uncaught exception.
* Color metadata is preserved in Generated Layout JSON (already true) and now in SVG (`data-color`).
* No forbidden file changed; no unrelated refactor.
* `TASK_RESULT.md` accurately reports what was verified vs. not.

## Implementation Constraints

* Smallest coherent change; no unrelated refactor of `app.js`, renderers, or geometry.
* Preserve millimeters throughout; preserve `Stone.color`/`layerId` metadata.
* Do not add a bundler, framework, or dependency.
* Do not change the Project JSON schema or the Generated Layout JSON schema (`StoneLayout.toJSON()`
  shape) — only add validation, an import path, and documentation around them.
* Do not modify geometry generation behavior to make an export test pass.
