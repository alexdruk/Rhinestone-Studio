# RS-0003.5B2 — Browser Dependency Loading

## Status

DRAFT — requires Claude specification review before implementation.

## Milestone

RS-0003.5B — Browser Integration

## Objective

Make the permanent text and geometry modules loadable in the browser without changing the application's generated layout, rendering, exports, controls, or visible behavior.

This task prepares the browser dependency boundary only.

The legacy `GeometryEngine` currently defined in `app.js` must remain the active runtime engine.

The permanent `src/geometry/GeometryEngine.js` must not generate the application's live layout during this task.

## Required Outcome

The browser must be able to resolve and import the permanent module dependency chain required for future geometry integration.

At minimum, the browser-loading path must support successful imports of:

* `OpenTypeProvider`,
* `FontManager`,
* the permanent text module exports,
* the permanent geometry module exports,
* the installed `opentype.js` dependency.

Successful loading means that the complete ES-module dependency graph resolves in the browser without module-resolution or MIME-type errors.

`OpenTypeProvider` must be imported but must not be instantiated during this task.

No font must be loaded for application use.

No permanent geometry class must generate the application's live layout.

---

## Dependency Strategy

`OpenTypeProvider.js` currently contains a bare module import:

```js
import opentype from 'opentype.js';
```

Browsers cannot resolve this bare package specifier through ordinary relative ES-module loading.

Therefore, the preferred implementation is:

1. Add an import map that resolves `opentype.js` to a local browser-loadable module from the installed npm package.
2. Continue using native ES modules and relative paths for all project-owned modules.
3. Add a minimal browser adapter only if the installed package cannot be loaded directly through the import map.

An import map or an equivalent browser-native mapping is required unless the specification is revised and re-reviewed.

Do not introduce a bundler.

Do not use a public CDN.

Do not copy the `opentype.js` source into project-owned source files.

Do not modify files inside `node_modules/**`.

Do not rely on a global browser variable such as `window.opentype`.

The application must work locally through:

```bash
npm run dev
```

## Architecture Requirements

* Project and geometry data remain measured in millimeters.
* `GeometryEngine` remains the source of permanent generated-stone geometry.
* `OpenTypeProvider` remains independent of the DOM and rendering code.

* Browser dependency handling must remain separate from layout generation.
* No permanent module may depend on `window`, `document`, Canvas, WebGL, or application controls.
* No renderer or exporter behavior may change.
* No new application state model may be introduced.
* No duplicate copy of the permanent geometry logic may be added.
* The legacy engine remains active only as a temporary migration dependency.

## Required Implementation

### 1. Browser dependency resolution

`OpenTypeProvider.js` currently uses:

```js
import opentype from 'opentype.js';
```

This import must continue working in both environments:

* Node, where the package resolves through its CommonJS/UMD entry point and exposes the API through a default export;
* the browser, where the package’s native ES-module build exposes named exports and does not provide a default export.

Because the same bare specifier resolves to structurally different module formats in Node and the browser, `src/text/OpenTypeProvider.js` must remain unchanged.

This task shall add a browser-only compatibility adapter under:

```text
src/browser/**
```

The adapter must:

1. import the local native ES-module build supplied by the installed `opentype.js` package;
2. expose the API shape expected by `OpenTypeProvider.js` as a default export;
3. include at least the `parse` function used by `OpenTypeProvider`;
4. contain no application logic, font loading, DOM access, rendering, or state mutation.

The browser import map must resolve:

```text
opentype.js
```

to this local adapter rather than directly to the package’s `.mjs` file.

Node resolution must remain unchanged because import maps apply only in the browser.

Do not:

* modify `src/text/OpenTypeProvider.js`,
* modify `node_modules/**`,
* copy the complete library into project-owned code,
* use a CDN,
* rely on a global `window.opentype` value.

The adapter must be documented in `TASK_RESULT.md`, including the exact local package module it imports.

### 2. Browser module probe

Add a narrowly scoped browser module whose only purpose is to verify that the permanent dependency graph can load.

Preferred location:

```text
src/browser/BrowserDependencyProbe.js
```

Equivalent naming is acceptable if another location better matches the repository architecture.

The probe must import:

* `OpenTypeProvider`,
* `FontManager`,
* the permanent text module exports,
* the permanent geometry module exports.

Importing `OpenTypeProvider` must cause its `opentype.js` dependency to resolve successfully through the browser mapping.

The probe must not:

* instantiate `OpenTypeProvider`,
* instantiate `FontManager` unless an import-only verification is impossible,
* load a font,
* generate stones,
* instantiate the permanent `GeometryEngine` for application use,
* mutate project state,
* access the DOM,
* render anything,
* perform exports,
* make any network request other than normal local module loading.

A small exported function or frozen status object may be used to prove that all imports completed.

The probe must not duplicate application or geometry logic.

### 3. Application entry-point loading

`app.js` may import the browser dependency probe.

The import must occur without changing application behavior.

The imported permanent modules must not replace, modify, wrap, or configure the legacy engine.

The import must not:

* instantiate the permanent `GeometryEngine` for live generation,
* instantiate `OpenTypeProvider`,
* load fonts,
* modify the default project,
* modify generated stones,
* modify application controls,
* change rendering,
* change exports,
* expose new global state,
* introduce user-visible startup behavior.

### 4. Failure behavior

A dependency-loading failure must appear as a clear browser module or console error.

Do not silently:

* fall back to a CDN,
* fall back to a global variable,
* skip loading the permanent modules,
* use an alternate geometry implementation,
* suppress module-resolution errors.
