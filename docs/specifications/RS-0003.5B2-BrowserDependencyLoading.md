# RS-0003.5B2 — Browser Dependency Loading

## Status

DRAFT — requires Claude specification review before implementation.

## Milestone

RS-0003.5B — Browser Integration

## Objective

Make the permanent text and geometry modules loadable in the browser without changing the application's generated layout, rendering, exports, controls, or visible behavior.

This task prepares the browser dependency boundary only.

The legacy `GeometryEngine` currently defined in `app.js` must remain the active runtime engine.

The permanent `src/geometry/GeometryEngine.js` must not generate the application's live layout during this task.

---

## Current Repository State

The repository already contains:

* a browser module entry point at `./app.js`,
* `index.html` loading `app.js` with `type="module"`,
* the legacy bitmap `GeometryEngine` inside `app.js`,
* permanent text modules under `src/text/**`,
* permanent geometry modules under `src/geometry/**`,
* `OpenTypeProvider`,
* the `opentype.js` npm dependency,
* local font assets,
* passing automated tests.

RS-0003.5B1 moved the live application from an inline script into `app.js`.

This specification begins from that state.

---

## Expected Visible Change

NONE.

After implementation:

* the default project must render exactly as before,
* the same stone count and layout bounds must be produced,
* the same bitmap text engine must remain active,
* the 2D layout must remain unchanged,
* the cup preview must remain unchanged,
* controls and exports must behave unchanged.

---

## Required Outcome

The browser must be able to resolve and import the permanent module dependency chain required for future geometry integration.

At minimum, the browser-loading path must support:

* `OpenTypeProvider`,
* the permanent text module exports,
* the permanent geometry module exports,
* the installed `opentype.js` dependency.

Successful loading must be verifiable without replacing the active engine.

---

## Dependency Strategy

Use the smallest browser-compatible solution that works with the existing no-build development server.

Preferred order:

1. Native ES modules with browser-resolvable relative paths.
2. An import map for bare package imports such as `opentype.js`.
3. A narrowly scoped browser adapter module when required.

Do not introduce a bundler merely for this task.

Do not copy the `opentype.js` source into project-owned source files.

Do not load dependencies from a public CDN.

The application must work locally through:

```bash
npm run dev
```

The browser dependency must resolve from repository-controlled local files or the installed npm package.

---

## Architecture Requirements

* Project and geometry data remain measured in millimeters.
* `GeometryEngine` remains the source of permanent generated-stone geometry.
* `OpenTypeProvider` remains independent of the DOM and rendering code.
* Browser dependency handling must remain separate from layout generation.
* No permanent module may depend on `window`, `document`, Canvas, WebGL, or application controls.
* No renderer or exporter behavior may change.
* No new application state model may be introduced.
* No duplicate copy of the permanent geometry logic may be added.
* The legacy engine remains active only as a temporary migration dependency.

---

## Required Implementation

### 1. Browser dependency resolution

Create or configure a browser-compatible method for resolving `opentype.js`.

The selected method must:

* work with the existing local static server,
* use no public CDN,
* require no global browser variable,
* preserve ES-module semantics,
* avoid modifying the installed package,
* be documented in the implementation report.

### 2. Browser module probe

Add a narrowly scoped browser module whose purpose is to verify that the permanent dependency chain can load.

Recommended location:

```text
src/browser/BrowserDependencyProbe.js
```

Equivalent naming is acceptable if the repository architecture clearly supports another location.

The probe must:

* import the required permanent text exports,
* import the required permanent geometry exports,
* make `OpenTypeProvider` load successfully,
* cause `opentype.js` to resolve successfully,
* expose no UI,
* generate no stones,
* mutate no project state,
* produce no rendering,
* perform no network request other than normal local module loading.

A small exported function or frozen status object may be used to prove that imports completed.

### 3. Application entry-point loading

`app.js` may import the browser dependency probe.

The imported permanent modules must not replace or modify the legacy engine.

The import must not:

* instantiate the permanent `GeometryEngine` for live generation,
* instantiate `OpenTypeProvider` for live text rendering,
* load a font for application use,
* modify the default project,
* modify generated stones,
* change startup timing in a user-visible way.

### 4. Failure behavior

A dependency-loading failure must appear as a clear browser module or console error.

Do not silently fall back to a CDN, global variable, or alternate geometry implementation.
