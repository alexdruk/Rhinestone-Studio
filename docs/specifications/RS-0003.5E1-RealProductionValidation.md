# RS-0003.5E1 — Real Production Validation

Status: implemented.

## Objective

Create a permanent, committed regression suite of representative production designs that proves
Rhinestone Studio's permanent Geometry Engine / StoneLayout / renderer / exporter pipeline behaves
correctly and deterministically on real-shaped inputs, not just synthetic unit fixtures. This is a
test/fixture milestone: it adds no new product feature and changes no export schema.

## Current repository state (inspected before implementation)

* `examples/` contains exactly two `.rhs` project fixtures (`vitalina.rhs`, `vitalina-serbin.rhs`),
  each a single-text-layer project using a **flat, mm-suffixed schema**
  (`heightMm`/`stoneSizeMm`/`gapMm`, `mode: "centerline"|"fill"`, `font` as a family display name).
  Nothing in the live app currently parses this schema.
* `app.js` owns a **different, ad hoc, non-mm-suffixed** in-memory project schema
  (`height`/`stoneSize`/`gap`, `textMode: "stroke"|"fill"`, `font` as a font *id*), produced by
  `defaultProject()` and accepted by `validateProject()` (the Project JSON import path added in
  RS-0003.5D1). This is the schema the live UI edits, exports, and imports.
* `src/core/Project.js`/`Layer.js` implement a **third** schema (`xMm`/`yMm`/nested `params`),
  unused by `app.js` (a deliberate, test-enforced exclusion — see `docs/ARCHITECTURE.md`
  "Current Architectural Limitations" #1).
* The permanent `src/geometry/GeometryEngine.js` (`generateTextLayout()`/`generateShapeLayout()`)
  is schema-agnostic: it takes flat mm-suffixed parameters directly
  (`heightMm`, `stoneSizeMm`, `gapMm`, `cxMm`/`cyMm`/`radiusMm`, `xMm`/`yMm`/`widthMm`/`heightMm`)
  and has no dependency on either project model.
* The cross-layer merge (dedupe-by-proximity across per-layer `StoneLayout`s, auto-fit rescale,
  and text centering) is orchestration logic that lives only in `app.js`'s local `GeometryEngine`
  bridge class (`generate()`/`generateTextStonesLive()`/`generateShapeStonesLive()`/`dedupe()`).
  This is a documented architectural gap (`docs/ARCHITECTURE.md` "Current Architectural
  Limitations" #2), not something this milestone is scoped to fix.
* `app.js` is a browser entry point (top-level DOM access, `fetch`) and is not `import()`-able
  under plain Node — every existing test that needs to exercise its logic either does structural
  regex assertions against its source text, or reimplements the exact same algorithm against the
  permanent modules directly (see `tools/test-ux-visual-polish.mjs` test 9, which reproduces
  `generateTextStonesLive()`'s two-pass auto-fit call sequence verbatim). This milestone follows
  that established precedent.
* Every existing `tools/test-*.mjs` forbidden-file guard (`test-app-module-migration.mjs`,
  `test-live-text-integration.mjs`, `test-shape-geometry-integration.mjs`,
  `test-render-export-pipeline.mjs`, `test-browser-dependency-loading.mjs`,
  `test-production-export-validation.mjs`, `test-ux-visual-polish.mjs`) currently lists
  `examples/` as a **forbidden-to-change** path prefix, because every prior milestone was
  correctly scoped to leave `examples/` untouched. This milestone's entire required outcome is to
  add files under `examples/`, so all seven guards must have `examples/` removed from their
  forbidden-prefix list. This is a small, direct, necessary correction — not unrelated cleanup.

## Resolved discrepancy: which "existing .rhs format" to use

The milestone brief says "use the existing project JSON / `.rhs` format" and requires preserving
the two existing `.rhs` files unmodified. Since the two preserved files use the mm-suffixed schema
(not `app.js`'s ad hoc schema — confirmed by running `app.js`'s literal `validateProject()` against
`vitalina.rhs`, which throws), the mm-suffixed schema demonstrated by the two preserved files is
treated as the canonical, permanent `.rhs` interchange format for this regression suite. All 15
new example files use the same schema. This is not a new project schema invented by this
milestone — it is the schema the two preserved fixtures already established; this milestone is the
first to formally document and validate it.

A pure, side-effect-free translator (`tools/lib/rhsProject.mjs`'s `toAppProjectShape()`) maps this
`.rhs` schema onto `app.js`'s ad hoc schema, used only by: (a) a Node-side test that feeds the
translated output through `app.js`'s actual, unmodified `validateProject()` function (extracted
from its literal source, matching the precedent in `test-ux-visual-polish.mjs`), and (b) the
browser-verification driver, which imports the translated project through the live app's real
`#importProjectFile` UI control. `app.js` and `index.html` are not modified by this milestone.
Because `app.js`'s import handler runs with `skipWrite=true` (no stale DOM control values
overwrite the imported layer fields) and both the Node-side generator and `app.js`'s live
`GeometryEngine.generate()` call the identical permanent `generateTextLayout()`/
`generateShapeLayout()` with identical parameters, identical auto-fit/centering logic, and an
identical proximity-dedupe formula, the two paths produce numerically identical `StoneLayout`s —
this is verified directly by the browser-verification pass (stone counts observed in the live app
match the committed baseline computed by the Node-side runner).

## Required outcome

* 15 new representative `.rhs` examples under `examples/`, in addition to the two preserved files,
  covering: short/long names, monograms, script font (Great Vibes), block font (Courier Prime),
  outline mode, fill mode, front wrap, wider wrap (wide/half/full), circles, rectangles, mixed
  text+shape layers, a hidden (invisible) layer, light and dark cup colors, varied stone sizes, and
  varied gaps.
* `examples/manifest.json` — machine-readable, one entry per example (including the two preserved
  files), describing its file name, human description, and validation-purpose tags.
* `examples/baselines.json` — committed, machine-generated-once, human-reviewed baseline geometry
  expectations per example: layer count, visible layer count, stone count, bounding box, font ids
  used, colors used, and a validation category. Regenerated only by deliberately running
  `tools/generate-example-baselines.mjs` (never by `npm test`).
* `tools/lib/rhsProject.mjs` — shared loader/validator/generator library (parses and structurally
  validates the `.rhs` schema; reproduces `app.js`'s merge/dedupe/auto-fit/centering algorithm
  against the permanent `GeometryEngine` directly; translates to `app.js`'s ad hoc schema for
  cross-checking against the real `validateProject()` and for browser import).
* `tools/test-examples-regression.mjs` — the automated runner/test suite (see below).
* Existing `npm test` suites continue to pass unmodified in behavior (only their forbidden-file
  guard's `examples/` entry is removed).

## Architecture requirements

* No change to `StoneLayout`, `Stone`, `GeometryEngine`, `SvgExporter`, any renderer, or any export
  schema.
* No change to `app.js`'s or `index.html`'s behavior or schema.
* All geometry generation in the new test infrastructure goes through the permanent
  `src/geometry/GeometryEngine.js` (via its `index.js` barrel) — the new `tools/lib/rhsProject.mjs`
  never invents stone positions itself; it only calls the permanent engine per layer and then
  filters (dedupes) already-generated positions by proximity, exactly mirroring the one place
  `app.js` does the same (documented architectural limitation, not newly introduced here).
* Millimeters throughout; deterministic output required and verified.

## Automated tests (`tools/test-examples-regression.mjs`)

1. Every `examples/manifest.json` entry points to an existing `examples/*.rhs` file, and every
   `examples/*.rhs` file has a manifest entry (bidirectional coverage).
2. Every example parses as valid JSON and passes `validateRhsProject()` structural validation.
3. Every example, translated via `toAppProjectShape()`, is accepted by `app.js`'s real
   `validateProject()` (extracted from its literal source and executed, not reimplemented).
4. Every example round-trips through `JSON.parse(JSON.stringify(...))` (both in its native `.rhs`
   shape and its translated app-shape) with no data loss (`assert.deepEqual`).
5. Every visible layer of every example generates a non-throwing per-layer `StoneLayout` via the
   permanent `GeometryEngine`.
6. Every example produces a deterministic merged `StoneLayout` (two independent generation runs of
   the same example produce identical `toJSON()` output).
7. Every example's actual stone count and bounding box match `examples/baselines.json` within a
   `0.001mm` tolerance on bounds (exact equality on counts — deterministic, no tolerance needed).
8. Every stone in every generated layout has finite `xMm`/`yMm`/positive finite `sizeMm`.
9. Every stone's `color` is a non-empty string, and the set of colors observed per example matches
   `examples/baselines.json`.
10. `StoneLayout.toJSON()` / `StoneLayout.fromJSON()` round-trips losslessly for every example.
11. `stoneLayoutToSvg()` produces well-formed SVG for every example: `<circle>` count equals
    `StoneLayout.count`, and every circle's `cx`/`cy`/`r` matches its source stone.
12. No `NaN`/`Infinity` anywhere in any generated `StoneLayout` or SVG output; no example with a
    manifest category expecting stones produces zero stones; no stone center lies wildly outside
    the project canvas (generous manufacturing tolerance, not a tight visual-margin check).
13. The two preserved example files (`vitalina.rhs`, `vitalina-serbin.rhs`) are present, unmodified
    (content byte-for-byte equal to the values recorded when this milestone started), and covered
    by the same validation/generation/baseline pipeline as the 15 new examples.
14. Example files are only ever read during the test run, never written — a checksum comparison
    before/after the suite proves no example was silently modified.
15. All prior `npm test` suites continue to pass (run as part of `npm test`, not duplicated here).

## Browser verification

At least 8 examples (short block text, long auto-fit text, Great Vibes script text, outline mode,
fill mode, circle-only, mixed text+shapes, dark cup with wider wrap) are imported into the live app
via the real `#importProjectFile` control (translated to `app.js`'s schema, per the discrepancy
resolution above), driven headlessly over raw CDP (matching the established
RS-0003.5B2–5D2 precedent — no new browser-automation dependency). For each: confirm import
succeeds, the 2D layout renders, the cup preview renders, stone count matches the committed
baseline, Generated Layout JSON and SVG export without error, and no console errors are logged.
Screenshots are captured for representative cases. A human-review readability table (2D
readability, cup readability, clipping, overlaps, visual notes) is recorded in `TASK_RESULT.md` for
only the examples actually inspected.
