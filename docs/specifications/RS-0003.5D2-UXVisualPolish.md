# RS-0003.5D2 — User Experience and Visual Polish

## Objective

Improve the usability and visual quality of the live application without touching permanent
geometry, the Project JSON schema, the Generated Layout JSON (`StoneLayout.toJSON()`) schema, or
the exporter architecture. This milestone is a rendering/interaction-layer polish pass on top of
the unified `StoneLayout` pipeline RS-0003.5C2 established and RS-0003.5D1 hardened — it changes
how things *look and feel*, not what geometry gets generated or exported.

Every visual defect fixed here was explicitly recorded as an out-of-scope "Warning" in
`TASK_RESULT.md` for RS-0003.5D1 (and, before that, RS-0003.5B3/5C1/5C2): the cup handle renders as
a detached schematic loop, cup drag rotation is far too sensitive to small mouse movements, and the
`#stoneSize` `<select>` shows blank on load despite the underlying layer having a valid stone size.
This milestone closes all three, plus the adjacent visual-polish items in the milestone brief
(cup body shading, selection/resize handle visibility, zoom robustness, text readability
verification).

## Current Repository State

* `src/renderer/CupRenderer.js` draws the handle as a stroked half-ellipse arc whose two endpoints
  (at angle ∓90°) share the same x-coordinate (`cx + side * topW * .5`), while the cup body's wall
  actually tapers from `topW` to `botW` — so the handle's lower endpoint does not line up with the
  narrower wall at that height, producing a visible gap ("detached schematic loop"). The visible
  side is also chosen by a **discrete** sign flip (`side = Math.cos(rot) >= 0 ? 1 : -1`) that
  changes at exactly `rotationDeg = ±90°` — precisely the "Left"/"Right" view-button angles — while
  `showHandle` (`Math.cos(rot) > -.35`) is still `true` there, so the handle visibly jumps from one
  flank to the other while fully opaque.
* The cup body fill is a 5-stop `createLinearGradient` with abrupt stop percentages
  (`0/.28/.52/.75/1`) that reads as banded/blocky rather than a smooth cylindrical shading falloff.
* `app.js`'s cup-drag handler (`cupCanvas` `pointermove`) maps mouse-pixel delta to rotation degrees
  1:1 (`rotation += e.clientX - lastX`) with no named constant — a 40px flick swings the cup 40°,
  far too sensitive for controllable small adjustments.
* `app.js`'s zoom is read as `(parseFloat(el('zoom').value) || 100) / 100` with no explicit clamp;
  the `<input id="zoom">` range (`min="70" max="140"`) constrains normal slider interaction, but
  nothing in `app.js` defends against an out-of-range or non-finite value reaching `zoom` if the
  control is ever driven programmatically.
* `syncSelectedControlsFromLayer()` sets `el('stoneSize').value = String(l.stoneSize)`. The
  default project's text layer has `stoneSize: 2` (a JS number), so this sets `value = "2"`, but
  `index.html`'s `<select id="stoneSize">` only has an option `value="2.0"` (plus `0.8/1.0/1.2/
  1.5/1.8/2.5/3.0`) — `"2"` matches no `<option>`, so the browser shows the dropdown blank despite
  `l.stoneSize` being a valid, correctly-stored `2`.
* `drawSelection()` in `app.js` draws a single 1.5px dashed blue rectangle and plain white/blue
  10×10px square handles with no contrast halo — low visibility against the light grid background
  and especially against light-colored stones or a light cup-adjacent panel.
* `drawStone()` in `src/renderer/CanvasRenderer2D.js` (shared by the 2D layout and the cup preview)
  draws a stone with no contrast ring behind it; a light stone color (e.g. Crystal AB) on a white
  or cream cup background can be low-contrast.
* Courier Prime and Great Vibes text generation (`GeometryEngine.generateTextLayout`) and rendering
  are unchanged by RS-0003.5D1/5C2; this milestone verifies (does not change) their readability
  across wrap modes and text modes per the milestone brief.

## Required Outcome

### Cup handle (`src/renderer/CupRenderer.js`)

* The handle attaches to the cup wall at both ends: the attachment x-coordinate at each end is
  computed from the same tapered-wall interpolation the body silhouette uses
  (`wallHalfWidthAt(y)`), not a single fixed offset.
* The handle's screen position and bulge are continuous functions of `rotationDeg` (built from
  `sin`/`cos` of a linear function of rotation, with a `smoothstep` fade — no discrete sign flip,
  no hard threshold flip while opaque). Rotating slowly through any angle, including exactly ±90°,
  never produces a visible jump.
* The handle is a closed, filled loop (outer bezier boundary + inset inner boundary) with a
  visible opening, gradient shading, a thin dark rim stroke, and small soft contact-shadow patches
  at both wall attachment points that visually fuse the seam into the body.
* The cup body is still drawn after the handle, so the body's own silhouette/stroke naturally
  overlaps and hides the true attachment seam (unchanged draw order from before this milestone).

### Cup body and lighting (`src/renderer/CupRenderer.js`)

* The body fill gradient is replaced with a smooth multi-stop cosine falloff (bright center,
  darker toward both silhouette edges) instead of 5 abrupt stops, removing the banded/blocky
  impression while keeping the same canvas 2D renderer (no WebGL).
* A subtle soft (alpha-faded, no hard edges) vertical sheen is added over the body fill for depth.
* Cup colors remain fully configurable (`cupColor` option unchanged; `shade()` helper unchanged).

### Rotation interaction (`app.js`)

* A named constant `CUP_ROTATION_SENSITIVITY` (degrees of rotation per pixel of horizontal drag)
  replaces the previous unexplained 1:1 mapping, set substantially below `1` so small mouse
  movements produce controllable rotation.
* The drag handler remains delta-based (`rotation += (e.clientX - lastX) * CUP_ROTATION_SENSITIVITY`)
  — no jump at drag start (no reset-to-absolute-position) or drag end (no snapping).
* View buttons and the rotation `<input type="range">` slider are untouched and continue to set
  `rotation` directly.

### Zoom interaction (`app.js`)

* Named constants `ZOOM_MIN`/`ZOOM_MAX` (matching the `#zoom` range input's `min="70"`/`max="140"`)
  are introduced and `zoom` is explicitly clamped to `[ZOOM_MIN, ZOOM_MAX]` after parsing, defending
  against any non-finite or out-of-range value reaching the renderer.
* The zoom control itself (`<input id="zoom" type="range">`) is not redesigned.

### Shape selection and resize feedback (`app.js`)

* `drawSelection()` draws a white contrast halo behind the existing dashed blue selection outline,
  and enlarges/soft-shadows the resize handles, improving visibility against any background.
* Hit-testing (`hitTest()`), drag, and resize math for circle/rectangle layers are unchanged; mm
  coordinates and geometry are unaffected — this is a drawing-only change.

### Text readability

* Courier Prime and Great Vibes are verified (not modified) across 2D layout, cup front view,
  front wrap, wider wrap modes, outline mode, and fill mode, per browser verification below.
  `GeometryEngine`'s sampling rules are not changed; no defect requiring a sampling change was
  found during this milestone (see Browser Verification).

### Stone-size dropdown (`app.js`)

* A new helper `setNumericSelectValue(select, num)` sets a `<select>`'s value to the option whose
  parsed numeric value is closest to `num`, instead of a brittle exact string match. Used by
  `syncSelectedControlsFromLayer()` for `#stoneSize`. The underlying `layer.stoneSize` millimeter
  value is unchanged; only the displayed selection is corrected.

## Architecture Requirements

* `src/renderer/CupRenderer.js` and `src/renderer/CanvasRenderer2D.js` remain StoneLayout-only: no
  reference to `Project`, `Layer`, a layer `type` string, or `GeometryEngine`/geometry-generation
  calls. All new drawing logic operates only on the `rotationDeg`/`zoom`/`cupColor`/`wrap` options
  and the `StoneLayout` already passed in.
* No geometry generation happens inside a renderer; `GeometryEngine`, `Stone`, `StoneLayout`,
  `src/text/**`, `src/fonts/**`, and `src/export/**` are not modified.
* `app.js` continues to only import the same permanent barrel modules it already imports (no new
  import added this milestone).
* Stone count and bounding box for the default project (and any unchanged project input) remain
  byte-identical before and after this milestone — verified by an automated `GeometryEngine`-level
  regression test and by browser verification of the on-screen stats.

## Required Automated Tests (`tools/test-ux-visual-polish.mjs`)

1. `CUP_ROTATION_SENSITIVITY` is defined in `app.js`, is a finite number strictly between `0` and
   `1`, and is the multiplier actually used in the cup `pointermove` handler (regex against the
   exact updated expression); the previous unscaled `rotation+=e.clientX-lastX` expression is gone.
2. Drag rotation delta behavior: for a representative pixel delta, the resulting rotation delta
   (recomputed from the extracted `CUP_ROTATION_SENSITIVITY` value) is substantially smaller than
   the raw pixel delta, and the `-180..180` clamp is still present.
3. `ZOOM_MIN`/`ZOOM_MAX` are defined in `app.js`, equal `0.7`/`1.4` (matching `#zoom`'s `min="70"`/
   `max="140"` in `index.html`), and `writeSelectedControlsToLayer()` clamps `zoom` with
   `Math.max(ZOOM_MIN,Math.min(ZOOM_MAX,...))`.
4. `setNumericSelectValue()` is defined and used for `#stoneSize` in
   `syncSelectedControlsFromLayer()`; the previous brittle `String(l.stoneSize)` assignment for
   `#stoneSize` is gone. The function's extracted source is executed directly (via `new Function`)
   against a mock `<select>`-shaped object built from `index.html`'s actual `#stoneSize` option
   values, proving `2` (a number) resolves to `"2.0"`, `1.5` resolves to `"1.5"`, etc. — no blank
   selection.
5. `CupRenderer.renderCup()` never throws across a full rotation sweep (`-180°..180°` in 5° steps,
   both `zoom` extremes) for every wrap mode, and a recorded geometry sample (first handle-path
   anchor coordinate) changes continuously across the sweep — no single-step jump beyond a bounded
   threshold — proving the handle-attachment fix removes the discrete side-flip discontinuity.
6. `CupRenderer.js`/`CanvasRenderer2D.js` still reference no `Project`/`Layer`/layer-type literal/
   `GeometryEngine`/geometry-generation call (extends the existing RS-0003.5C2/5D1 guard to the
   files this milestone touches).
7. `drawSelection()` in `app.js` includes a contrast halo pass and an enlarged handle-size constant
   (structural check).
8. Geometry regression: calling the permanent `GeometryEngine.generateTextLayout()` with the exact
   parameters `app.js`'s default project's text layer uses produces the same stone count and
   bounding box recorded by this milestone (locking in "unchanged for unchanged input").
9. Export regression: `stoneLayoutToSvg()` and `StoneLayout.toJSON()` output for a fixed,
   representative `StoneLayout` are unchanged (byte-identical to a recorded expectation) —
   `src/export/**` and `src/geometry/**` were not touched this milestone, so this locks that in.
10. No forbidden file changed (this milestone's own forbidden list, including the updated allowance
    for `src/renderer/CupRenderer.js`/`src/renderer/CanvasRenderer2D.js`).
11. All prior suites (`npm test`) continue to pass unmodified in behavior (only the one guard-list
    update in `tools/test-production-export-validation.mjs`, matching the RS-0003.5D1 precedent of
    updating a forbidden-file allowlist when a file becomes legitimately in-scope).
