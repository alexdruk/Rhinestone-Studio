|`assets/fonts/Montserrat-Regular.ttf` is Montserrat **Thin**, not Regular|READ-003|**Resolved by FONT-LIB-005:** the library ships without Montserrat. The bundled file is byte-identical to Google Fonts' official *variable* Montserrat (the `Montserrat[wght].ttf` file under their OFL directory), whose `wght` axis defaults to 100 — so `opentype.js` renders its default instance as Thin. Google publishes no static Regular to swap in; producing one means instancing the variable font at `wght=400`, which needs Python `fontTools` for a single binary. Not worth it — Poppins already covers the modern-sans role at 400/600/700. The manifest now carries `montserrat-regular` as `"style": "Thin"`, `"weight": 100`, `"enabled": false`. The `.ttf` is **retained** so projects that already use Montserrat keep rendering byte-identically. See `docs/specifications/FONT-LIB-005-MontserratRetired.md`. Original finding: the bundled file reports `usWeightClass = 100` (Anton and Great Vibes both report 400). It ships under the `montserrat-regular` id and a "Regular" style label, so anyone picking Montserrat in the font library silently gets a hairline weight — its measured `stemWidthRatio` (0.0145) is the lowest in the library by a wide margin. Independent of readability.|

|The READ-010 warn-only readability floor does not apply to `providerId: 'rhinestone'` fonts|READ-011C|`textHeightBelowReadableMinimum()` (`app.js`) gates on `layer.height ÷ layer.stoneSize`, but `RhinestoneFontProvider` (`src/text/rhinestoneFont/RhinestoneFontProvider.js`) does not scale authored stone positions by `heightMm` — the READ-011C audit measured a constant 21.40 mm ink height and constant stone count for `rs-block` / `rs-modern` across every specified height. So the below-floor warning can fire when the rendering is actually fine and stay silent when it is not, and `#heightFixToFloorBtn` "fixes" it by writing a new `layer.height` that clears the warning while leaving the stone output byte-identical. |`rsBlock.js` / `rsModern.js` hardcode `PITCH_MM = 3.1` with no stone-size awareness|READ-011C|**Resolved by FONT-PITCH-001:** the overlapping pairing is no longer reachable through the Stone Size picker — `rs-block` / `rs-modern` now carry `unsupportedStoneSizes: ["ss16", "ss20", "ss30"]` in `assets/fonts/manifest.json`, so `updateStoneSizePrintableCapabilityUI()` disables those options for an authored-font text layer and `updateStoneSizeOverlapCapabilityUI()` explains the fixed-grid cause for a project that already holds such a pairing. `PITCH_MM` is unchanged — 3.1 mm is the font's authored design, not a defect, and `tools/test-font-pitch-001-authored-stone-sizes.mjs` derives the excluded set from the real glyph maps + kerning so the manifest can never drift from it. Original finding: `src/text/rhinestoneFont/families/rsBlock.js` and `src/text/rhinestoneFont/families/rsModern.js` place every authored stone at `col * PITCH_MM` with `PITCH_MM = 3.1` (SS10's 2.8 mm stone + 0.3 mm gap). `GeometryEngine` then stamps each stone with the layer's selected `stoneSizeMm`, so pairing a Production Font with SS16 (4.0 mm) or SS20 (4.7 mm) places overlapping stones — verified: `rs-block` "Vitalina" holds a 3.100 mm nearest-neighbour at every size, giving 64 overlapping pairs at SS16 and 87 at SS20. Nothing in the pitch is stone-size-derived. READ-011C investigated (no code change) whether the UI prevents that pairing: there is **no `providerId: 'rhinestone'`-specific stone-size constraint**. `updateStoneSizePrintableCapabilityUI()` gates only on printable height and the manifest `unsupportedStoneSizes` list (empty for both authored fonts). The general overlap sweep `updateStoneSizeOptionAvailabilityUI()` *does* generate each candidate layout and would disable the SS16 / SS20 `<option>`s for an active `rs-block` text layer — but it never disables the *currently selected* size (only flags it with `#stoneSizeOverlapWarning`), and it is PERF-gated to re-run only on selection change or `#stoneSize` focus, not on a font switch. So reaching `rs-block` + SS16/SS20 by switching font on an existing SS16 layer, or by loading / importing a project, leaves overlapping stones with only a warning banner; the fix is a separate milestone.|
|The READ-011 rating pass returned no floor and the successor manipulation is unwritten|READ-011E|The 147-specimen READ-011 rating pass landed, but READ-011D's §6 selection rule could never adopt Form A — its ±0.25-stone tolerance was unsatisfiable against a single shared ratio cut grid spanning three regimes whose pool-median `stemWidthRatio` values span 3.05× — and Form B was power-capped: in `monoline\|outline\|untracked` only cut 16 ever reaches the 12-row clearance minimum, so the best Form B could return in outline is the value `MIN_HEIGHT_TO_STONE_RATIO` already holds. `MIN_HEIGHT_TO_STONE_RATIO` therefore remains **16 and warn-only**; no per-regime floor is shipped. The recommended successor is a different manipulation, not a re-fit — sample on the stones-across-stem axis directly with a per-regime ratio grid so every regime straddles the same candidate stone counts (READ-011E §10). Its design, cut grid and clearance rule belong to its own pre-registration milestone and are not yet written.|
|Three-letter interlocked script is SS6-only — every larger stone size returns `CHAIN_TOO_THIN` for the `none` frame|MONO-015|The `'script'` layout's natural mark width scales linearly with the stone size (`singleChainHeightMm` is `0.85 · stoneSizeMm / stemWidthRatio`, and mark width is proportional to height). For Great Vibes "AKL" the natural padded mark is **136.5 mm at SS6** — inside the `none` frame's 150 mm cap (`COMMON_SCALING_LIMITS_MM` in `src/geometry/FrameLibrary.js`, applied to the Frame Size fields) — but **191.1 mm at SS10, 273.0 mm at SS16 (SS16 is 4.0 mm per `src/renderer/StoneSizes.js` — any table showing 3.8 mm is wrong), 320.8 mm at SS20, 436.8 mm at SS30**. Above SS6 the mark must shrink to fit, which drags the stem below the single-chain minimum, so "AKL" / SS10+ / `none` frame always fails. Documented in `docs/specifications/MONO-013-Interlock.md` §5 with no backlog entry until now. **MONO-015 weight sizing does not relieve it:** an assigned stone only widens the *bounding box*, through the per-stone half-diameter padding `StoneLayout.getBoundingBox()` adds (`src/geometry/StoneLayout.js`) — about 2 mm total for the two end stones — not the mark's point spread, which is fixed by the font geometry. The real fix (its own milestone) is either a larger frame allowance for the script layout or an authored-pitch relaxation; docs-only change here.|
|The `CHAIN_TOO_THIN` message quotes a non-monotonic, wrong stem-stone figure for OpenType slot-layout monograms — it reports the first sub-floor letter, not the binding one|MONO-016 (diagnosed MONO-017, resolved MONO-018)|**Resolved by MONO-018:** the single-chain minimum gate is hoisted out of `MonogramGenerator.generate()`'s per-letter OpenType loop. Every letter is now fitted before the outcome is decided, and on failure the **binding** letter is reported — the one with the minimum `achievedStemStones`, ties broken on the lower slot index. For Great Vibes `A,K,L` / `equal-three` / `none` / SS6 the reported figure is now `K` at 150×150 / 120×120 / 100×100 = 0.470 / 0.376 / 0.309 (strictly decreasing; the 0.591 up-tick is gone). The message gains a sub-floor count (`2 of 3 letters fall below`) and `diagnostics` gains `allLetterStemStones` (every letter's fitted stem, in slot order). `CHAIN_TOO_THIN` still emits `layers: null`, so no committed geometry baseline moved (MONO-012/013/014/015/016 suites re-run clean). `INVALID_FONT` and `FITTING_FAILED` inside the loop still fail fast — only the `CHAIN_TOO_THIN` gate defers. The rejected alternative (keep fail-fast, reword the number as one-of-several) and its cost figures are in `docs/specifications/MONO-018-BindingLetter.md`. **Diagnosed in `docs/specifications/MONO-017-StemReportDiagnosis.md` — reporting defect, not a fitting defect; no geometry is affected.** `MonogramGenerator.generate()`'s per-letter OpenType branch in `src/monogram/MonogramGenerator.js` (the `for` loop at line 722, gate + fail-fast `return` at lines 791-802) quotes `achievedStemStones` for the **first letter in slot-index order** below `minChainStones`, not the minimum across letters. Different letters shrink by different amounts to fit an identical slot, so the identity of the first sub-floor letter changes with frame size: for Great Vibes `A,K,L` / `equal-three` / `none` / SS6 / `letterSpacingMm` 0 the reported figure is **K 0.470 at 150×150, K 0.376 at 120×120, A 0.591 at 100×100** — non-monotone only because `A` (i=0) clears the 0.70 floor at 150/120 and drops below it at 100, taking over as the reported letter while the true worst letter (K, 0.310 at 100×100) is never evaluated. Every individual letter's fitted height is monotone in frame size; the fit loop converges in 1–5 of its 6 iterations and the earlier "landing on the iteration cap" hypothesis is disproved. `generate()` returns the correct `CHAIN_TOO_THIN` outcome and emits no geometry at every size — only the quoted number is wrong. Generalises to `two-letter` / `traditional-three` / `equal-three` with any OpenType font + ≥2 letters; not `script` (one joined string) and not authored fonts (no stem figure). Fix (its own milestone, message/diagnostics only, no baseline moves): report the binding letter — see MONO-017 §5.|
|Monogram layer ids are deterministic, so regenerating the same frame+layout twice into one project collides|MONO-014|`MonogramGenerator.generate()` builds every layer id from `frameId` / `layoutId` alone (`monogram-${frameId}-${layoutId}-frame`, `monogram-${frameId}-${layoutId}-letter-N`). Generating a second monogram with the same frame and layout into a project that already holds one produces duplicate layer ids; `validateProject()` (`app.js`, the normalization gate every imported/autosaved/recovered project passes through) rejects a project with non-unique layer ids, so the collision surfaces on the next autosave-recovery / import / save round-trip rather than at generation time. Latent since MONO-005/006 — the ids have always been frame+layout deterministic. Fix (its own milestone): give generated monogram ids a per-generation unique suffix (a short random token or a `project`-scoped counter), the same way `insertLibraryItem()` already re-ids inserted library layers.|
